## 1. Coding standard

### 1.1 Po Game Standard (Unity / Unreal RL games)

This repo is one of several independent Po games. It follows the conventions below, but it owns every file:
nothing is generated from, synced with, or required to stay identical to another repository (no "same file in
every game" headers, no sync scripts that copy into other repos). Third-party code it needs (ML-Agents, MuJoCo
plugins, URLab) is vendored INSIDE this repo at a pinned version. Azure resources may be shared through `PoShared`.

#### Repo skeleton
```
README.md   AGENTS.md (this standard + repo notes)   CLAUDE.md ("Read AGENTS.md.")
docs/       lowercase, all prose (no DOCS/, no root DESIGN.md/SPEC.md/tasks.md — move them into docs/)
scripts/    build/publish/helper scripts (Unity: Tools/ is renamed scripts/ unless Unity itself needs it)
.github/workflows/<one file>.yml   the ONLY workflow
pyproject.toml with a [tool.ruff] section for any Python in the repo
```
No absolute local paths (C:\Users\...) committed anywhere. No build outputs or node_modules tracked.

#### Web page around the game (WebGL template / web viewer)
- The page chrome is drawn ONCE, by the HTML page, OUTSIDE the game canvas, so it can never overlap the HUD:
  a 44px top bar (game name top-left, settings gear / fullscreen top-right) and the version `vYYMMDD` bottom-right
  in the bar's counterpart or a 20px footer strip. The canvas fills the remaining viewport.
- The in-game HUD does NOT repeat the game name or version (it may show them inside menus, not as corner chrome).
- Same tokens as the web apps: dark background `#0b0f17`, surface `#121826`, text `#e6e9f2`, muted `#9aa3b5`,
  accent `#6366f1`, Inter/system-ui font. Text ≥ 4.5:1 contrast.

#### Orientation (C11)
The canvas fills any viewport (no fixed portrait aspect, no pillarboxing). UI is anchored and DPI-scaled
(Unity: CanvasScaler "Scale With Screen Size" or UI Toolkit PanelSettings scale-with-screen; Unreal: UMG anchors +
DPI curve). Must be checked at 1600x900 (landscape) and 450x800 (portrait) — screenshots in the PR/commit notes.

#### Version
One stamp, UTC `yyMMdd`, computed once by the publish/build script and injected into: index.html, diag.html,
and the player (`PlayerSettings.bundleVersion` / Unreal ProjectVersion) so `Application.version` matches the page.

#### /diag (games)
`/diag` (static `diag.html` generated by the publish script) titled **System status**, same layout as the web apps:
overall banner, then **API / Data / Services** sections. It must LIVE-probe (fetch from the browser, with latency)
every external dependency the game really calls (leaderboard tables/functions, weather APIs, AI APIs, replay bundles,
model files), plus the WebGL2 capability and that the build bundle files exist. Nothing hard-coded as "Ready".
The checks are listed in the repo's own config (e.g. `scripts/webgl.json` → `diagChecks`).

#### In-game diagnostics overlay (C12)
`Tab` (and a 44px corner button on touch devices) toggles an overlay showing: FPS, current episode reward,
inference latency (ms, rolling average), curriculum stage. Readable text (≥ 4.5:1 on an opaque panel).

#### Demo mode (C13)
After 30 s with no input (keyboard, mouse, touch, gamepad) from load or from last input: hide non-essential HUD,
all agents are driven by the trained policy (inference only), showcase cameras cycle (~6–8 s each); any input
returns control and the HUD. Idle threshold, camera list and dwell time are editor-tunable assets.

#### Rewards + editor-first config (C9, C10)
Reward includes penalties for joint torque², joint angular velocity², action rate ‖a_t − a_{t−1}‖², and foot sliding
(foot planar speed while in contact), each with its own weight. Reward weights, curriculum thresholds, cameras and UI
references live in ScriptableObjects / `[SerializeField]` (Unity) or DataAssets / `UPROPERTY(EditAnywhere,
BlueprintReadWrite)` (Unreal); Python trainers read the same values from the repo's training config. Changing a
penalty does not retrain shipped policies — note this in docs when shipped models predate the change.

#### Workflow
- Unity: the WebGL player is built locally with the EXACT pinned editor (Unity cannot be licensed in CI) by
  `scripts/publish_webgl.ps1`, which runs EditMode tests first, then builds, zips and publishes a `webgl-*` release.
  The one workflow: on release → deploy to the game's Static Web App → check the live page AND /diag; on push →
  Python checks (`ruff check`, `ruff format --check`, `pytest`) only.
- Unreal: the one workflow builds and deploys the repo's web front (viewer / showcase + /diag) to its Static Web App,
  after Python checks. The Unreal project must compile from a fresh clone (all plugins vendored in `Plugins/`).

#### Tests
Python: real pytest tests (collected by pytest, not ad-hoc scripts), ruff clean. Unity: EditMode tests pass before
every publish. Tests never write into tracked files.

### 1.2 House rules

Scope: RL-trained humanoids and animals with realistic motion on Earth, in Unity or Unreal.

#### Workflow & Setup
- **Git:** Work on `master`. Commit before syncing or pulling. Check `docs/` first.
- **Automation:** Set up scenes, prefabs and levels via CLI and headless Blender. UI changes get before/after screenshots and an HTML report in `SCREENSHOTS/`.
- **Build stamp:** Show the build date (`YYMMDD`) in the bottom-right corner.

| | Unity | Unreal Engine 5 |
|---|---|---|
| Background | Enable Run In Background | Disable Use Less CPU when in Background |
| Raw assets | `Assets/Art/Raw/` | `Content/Art/Raw/` |
| Exported assets | `Assets/Art/Exports/GLB/` | `Content/Art/Exports/` |
| Physics | MuJoCo (`org.mujoco`), not PhysX | MuJoCo / URLab, not Chaos |
| Policy runtime | Unity Sentis / ONNX | NNE / ONNX Runtime |

#### Physics & Realism
- **Collision:** Primitive colliders only (capsules, spheres, boxes). Non-adjacent parts collide with each other. Zero penetration at rest, at joint limits and through motion.
- **Fidelity:** Gravity −9.81 m/s², anatomical mass, realistic joint, torque and speed limits. Skeleton joints match between the 3D files and the simulator.
- **Smooth motion:** Rewards carry action-rate/jerk penalties (or low-pass filtering): fluid motion, no jitter.

#### Policy Architecture & Retraining
- **Hierarchy:** A few small policies, one per motor skill family (locomotion, balance/get-up, task skills). Cover variants with command inputs (velocity, gait, target, style), not new policies. Layered rule-based directors (game flow → body → skill) switch policies on physical state (contacts, centre of mass, falls) through one transition table, mirrored in every runtime. Policies never pick each other.
- **Hand-overs:** All policies of a body share the observation layout, joint order, action map, timing and motion-style reward. Preload every policy. Pass on the last action; never snap poses or blend outputs. Train each policy on the states it inherits (get-up from real falls).
- **Frozen interface:** Append inputs only at the end, with zero-initialised weights; never reorder or remove them. If the interface must break, distil the old policy into the new layout.
- Every new character gets its own training run and its own policies. No character reuses another's brain, even when the bodies are similar. Personality comes from the character card's traits and its own style reward weights, learned in training. Directors don't script it. Each character trains from scratch, passes every ladder level and the gate, and trains against the existing roster. Once a character is trained try to avoid retraining an existing character fully.
- **Before any change:** List the policies it touches (body physics → that body's; rules → the policies acting under them; new skill → its policy plus director rows; visuals → none) and log that in `docs/`. Afterwards, re-run every policy's regression scenarios (task + realism). Tag each checkpoint with its interface and physics versions.

#### Training, Gates & Reports
- **Execution:** Close the editor for runs over 30 min or when free RAM drops below 4 GB. Save and commit first.
- **Cleanup:** Delete failed runs, short tests (<5,000 steps) and unneeded checkpoints. Never delete a run written to in the last 24 h or one a queue will resume.
- **Graduation gate:** Export ONNX only after the target score holds for 100 straight episodes with no NaN gradients.
- **Telemetry:** Run TensorBoard with every run. Log metrics and progress to `docs/<YYYYMMDD>/` so later agents can pick up where a run left off.
- **Reports & updates:** Runs over 30 min get an HTML report with metric charts and run-over-run deltas. Estimate training time at startup. Send hourly updates (status grid, key improvements, short summary).

#### Communication
- **Large changes:** Over 100 lines of code: offer 3 roadmap/architecture questions.
- **Summary:** Responses over 100 words end with a ~20-word TL;DR.
- **Problem solving:** End with a proposed fix for the app's main open issue and ask before acting on it.

### 1.3 CI/CD and Azure

- WebGL is built **locally** and deployed by CI: `pwsh -File scripts/publish_webgl.ps1` runs the EditMode tests, builds
  `Builds/WebGL` with the exact pinned Unity (build method from `scripts/webgl.json`), writes `diag.html`, zips it and
  publishes a GitHub Release tagged `webgl-<yyMMdd-HHmm>-<sha>` (UTC; HEAD must be pushed first; releases are kept unless `-Keep N`).
  Publishing the release runs `.github/workflows/webgl.yml`, which deploys the zip to the Azure Static Web App
  `poolympic` (resource group PoOlympic) and checks the live page and /diag. CI has no Unity licence and needs none.
  Repo secret: `AZURE_STATIC_WEB_APPS_API_TOKEN`. Re-deploy an older build: Actions → Deploy WebGL → Run workflow (tag,
  empty = newest). `scripts/deploy_webgl.ps1` deploys `Builds/WebGL` straight from this PC without GitHub.
- Every push, pull request and release runs the Python checks (`ruff check`, `ruff format --check`, fast pytest tier).
  Only a `webgl-*` release (or a manual run) deploys, and only after those checks pass; the deploy stamps the
  release's commit into every response as `X-Commit` and checks the live X-Commit, page version and /diag.
- Tests pass on any machine: no drive-letter, temp-folder or working-directory assumptions, and no live config value
  hard-coded as an expected result (read it from the same config the app reads).

### 1.4 Working in this repo

#### Layout
- `Assets/_Project/Core/Runtime` game code (events, `PolicyRunner`, HUD, camera, audio) · `Editor` scene builders (`EventScenes`, `BroadcastFx`, `StadiumShowcase`) · `Tests/Editor` EditMode tests · `UI` USS / UXML (`Tokens.uss` = the design tokens).
- `Training/poolympic` contract, tasks, events (Python mirror of the Unity events) · `Training/tools` queue, gates, exports · `Training/runs` checkpoints (git-ignored).
- `parity/` (git-ignored, local) gate reports, candidate brains (`parity/brains`), reference trajectories, review pages (`parity/tb/<run>`), UI captures (`parity/ui`). Part of it is tracked (brains, reference trajectories); reports and candidates are local. UI before/after reports go in `SCREENSHOTS/`.
- `scripts/` publish / deploy / editor helper scripts · `Training/config/` training settings shared with Unity (reward penalties).
- Brain names: deployed = `<role>_<body>.onnx` (`crawl_kim`, `slope_matt`; MATT's oldest are `rung0` / `rung2` / `rs_v8_it1199`) + `.critic.onnx`, listed in `parity/brains/manifest.json`; candidates = `<run>_it<N>.onnx`, never copied into Unity (`ParityHarness.SyncArtifacts` syncs only brains the manifest or the C# names).
- History: `docs/log/` (September log entries, finished task sections); `docs/rl_optimization_log.md` / `docs/tasks.md` hold the current ones.

- Scene rigs are built by editor code, not by hand: after changing `BroadcastFx.Install` run the menu "PoOlympic/Broadcast/Upgrade broadcast FX (all event scenes)". To move something by hand in an event scene and keep it across rebuilds, add the `HandTuned` component to it (`HandTunedSave.SaveBuilt` restores its local transform by hierarchy path).

#### Things that bite
- Play mode starts **without a domain reload**: every static needs a `[RuntimeInitializeOnLoadMethod(SubsystemRegistration)]` reset (see `DemoMode`, `MeetLineup`, `GameSettings`).
- Runtime code may not call `Instantiate` / `Destroy` or any PhysX API (`RuntimeRulesTests`); new scene objects go through the editor builders as pools.
- Brains are tied to the model fingerprint and observation contract: never change `Training/assets/*.xml`, `contract.py` dims or an existing task's config in place — add a new task ID / contract version.
- Scenes are loaded only through `MeetLineup.Load`.

## 2. Concurrent work

- One branch: `master`, locally and on GitHub. Commit before you `git pull --rebase`; never force-push or rewrite pushed
  history. Several agents may work here one after another: read `git log -20` and `docs/` first and keep the owner's
  recent decisions.
- One engine at a time: a batch-mode Unity (tests, builds, `publish_webgl.ps1`) cannot open the project while the
  editor (or another batch Unity) has it open. Close the editor first, run one Unity job at a time, and run only one
  headless browser at a time. Close everything you started when you finish.
- Training runs own the GPU and `Training/runs/` (queue: `Training/runs/queue.txt`): do not start a second run, do not
  move or delete a run written to in the last 24 h, and close the editor for runs over 30 min.
- Tests never write tracked files: the parity gates write `parity/` reports (ignored), Unity results go to `Temp/` or
  `Builds/` (ignored). A clean `git status` after a test run is part of the check.
- The live site is a free-tier Static Web App: see **Hosting** in section 1.1 for the live-check budget.
- Deploys: only through a `webgl-*` release (`scripts/publish_webgl.ps1`) at a pushed commit; the workflow stamps that
  commit as X-Commit. Releases are not deleted by default (`-Keep N` opts into pruning).
- Brains and MJCF are shared contracts between Unity and the trainer: a change to `Training/assets/*.xml`,
  `contract.py` or a task cfg goes through a new task ID / contract version (see Things that bite).
